## Public command and small API

Add `flex-photo process SOURCE --destination DESTINATION --json-output OUTPUT --window-seconds 180 --tesseract EXECUTABLE --tessdata DIRECTORY --tesseract-sha256 SHA256`. Explicit local asset arguments map directly to `InterpretationAssets`; do not add a model downloader, asset registry or calibration interface. Preserve `discover`, help/version and `python -m flex_photo`. Accept a finite nonnegative window representable by the grouping API; the default remains 180 seconds.

Use one batch entry point, `process_batch(source, destination, output, *, assets, window) -> BatchResult`, plus focused serialization/filesystem helpers where needed. `BatchResult` contains complete/incomplete status, report path when saved and counts; CLI prints that small JSON summary. Exit 0 means complete (ordinary nonmatches, exact repeats and reported date exceptions are normal); exit 1 means incomplete or a processing/storage/conflict failure; argparse retains exit 2 for invalid syntax. Skipped qualifying timestamps, execution failures, overlaps and pending operations cannot be claimed completed.

Resolve and validate source, destination and output before effects: they are separate, nonnested directories. Source must exist; explicitly requested missing destination/output directories may be created. Reject unsupported link/reparse destinations or changed path identities when safe containment cannot be verified. Never follow a discovered link contrary to the existing discovery contract. Folder creation, report/state writes and private recovery files are distinct from photo moves/monthly publication.

## Preflight and value resolution

1. Create a unique per-run report independently of business output and acquire exclusive output-state ownership. Validate shared assets before processing or recovery. Missing/unavailable shared assets stop incomplete with no photo moves or monthly changes.
2. If pending work exists, verify and resume only that saved plan in this invocation; do not interleave a fresh batch. Validate recorded source/destination/output identities. After recovery completes, a subsequent normal invocation can process new photos. Recovery cannot silently change its saved window or output values.
3. Otherwise discover candidates, hash each source before/after interpretation to bind observations to unchanged original bytes, interpret serially and parse qualifying original timestamps. Nonmatches remain untouched; per-photo failures and missing/rejected capture times remain untouched/report/continue. Readings and anchors are limited to the approved scope. A source changing during preflight is skipped/reported.
4. Reuse `group_capture_times` and `latest_clear_indices` unchanged. Resolve each requested reading independently through exact decimal/duration equality and literal units under the monthly contract. Clear zero remains valid; unavailable fields retain an earlier clear candidate or null. Conflicting equally latest clear values stop the entire preflight before photo moves/monthly changes, preserving the report.
5. Construct complete trip entries, original membership, approved date/month and collision-safe movement plans. Preserve original capture-bound spellings. UTC-date overflow is a reported preflight error, never truncation/wraparound. Reconcile existing output before saving a pending plan and beginning effects. Revalidate shared assets after interpretation/preflight so mid-processing asset loss also prevents all business effects.

## Repeat identity and overlap reconciliation

Public monthly JSON remains exactly the approved schema. Use original-byte SHA-256 membership privately, never equal readings or array positions, to identify already processed trips. Keep one versioned private JSON sidecar, `.flex-photo-state.json`, in the output directory. It stores committed trip memberships and capture instants, grouping window, month, public entry digest and expected monthly file hashes. This is necessary because originals move and public JSON intentionally has no photo identity. It is not an additional public output field or database.

Within one invocation, byte-identical input copies count once for membership; select a deterministic path, report extra copies and leave them untouched. Before grouping unknown captures, compare supplied known hashes with indexed trip memberships: a complete indexed membership is an exact repeat, skipped without rewriting entries or moving its repeated copies; a supplied subset/shared membership is an overlap, reported and left untouched for reconciliation.

For remaining new captures, group with the configured window and compare against indexed capture history across month boundaries. Run the approved partition on the union of indexed and new capture instants. Any union group mixing new and indexed membership, or new captures that change a touched indexed trip's membership, requires reconciliation: skip/report affected new trips and leave existing records unchanged. An existing-only regrouping difference caused by a different current window does not rewrite history or block unrelated new trips. Store the window per committed trip rather than permanently locking the entire output directory to its first run's window. Thus old captures at minutes 2/5 plus new minute 1 overlap at a three-minute window; old 0/3 plus new 4 can append separately.

Reconcile to a stable accepted set before effects. Keep the original new candidate trips fixed. Partition indexed captures together with all currently eligible new candidates; simultaneously remove whole candidates involved in mixed groups or changed touched indexed memberships, then repeat using only surviving candidates. Rejected captures must not shield another candidate from overlap. Stop when a pass removes none or no candidates remain; removal is monotonic and bounded by the original candidate count. Preserve the old-only changed-window exception. For example, with window three minutes, indexed minute 0 and new minutes -3/1/2/4 initially produce candidates [-3] and [1/2/4]. Removing [-3] exposes the second candidate's overlap with indexed 0, so both are rejected; independently disjoint trips remain eligible.

Append only disjoint new trips, preserving every existing entry's values/order. New entries follow the monthly contract's ordering within this run. Validate sidecar/schema versions, indexed entry digests and expected monthly hashes before effects. A missing/inconsistent index for an existing monthly file, external edits or unknown schema prevents effects on the affected month/state and is reported; do not infer/import identity. Unrelated work continues only where its state is independently verifiable. No automatic repair/import or manual reconciliation command is introduced.

## Durable effects and safe resume

Use an OS-held nonblocking lock on `.flex-photo.lock` (`msvcrt` on Windows, `fcntl` on Linux), held for state validation, effects and recovery. The OS releases ownership when the process exits; a leftover lock file is not stale ownership. Concurrent ownership is refused and reported. One writer updates the sidecar through flushed temporary JSON and atomic replacement; retain expected hashes and never overwrite changed/unverified state.

Persist pending work before changing originals. It contains the complete resolved trip entries, source/destination paths and source hashes, reserved names, per-file progress, and any in-flight monthly publication's before/after hashes and complete planned bytes. Keep this in the same sidecar, alongside committed membership. Retain no excluded dashboard evidence. Flush state before irreversible source deletion so restart does not depend on reconstructing readings from remaining sources.

Process trips serially; isolate per-trip movement failures so another verified disjoint trip can proceed:

1. Allocate destination names without overwrite using the original stem and `-01`, `-02`, etc.; an already suffixed stem remains intact. Copy through an exclusively created private destination temporary file, flush it and verify complete SHA-256 against the unchanged source. Publish the final name with a no-overwrite operation; if a racing collision appears, allocate the next suffix and persist the revised reservation. Unsupported publication must fail safely rather than fall back to overwriting.
2. Persist the verified destination identity, then recheck the source hash before deleting that source. If either identity is unexpected, preserve both and report. A failed copy/delete retains originals, verified copies and pending evidence. Do not emit a completed trip until all its required movements are verified. Completed earlier trips remain completed.
3. For a movement-complete trip, build its monthly append from the currently verified file, and persist an in-flight publication containing the full before/after bytes/hashes and trip identity. Flush a temporary monthly JSON and atomically replace only the expected old file. Then atomically mark membership committed and update the expected month hash in the sidecar. Keep pending entries for incomplete trips. A publication/state failure blocks dependent work until that shared state is verified; it does not invalidate earlier verified progress.

On restart compare actual files with saved hashes. A recorded destination matching the full source hash needs no recopy; delete a remaining source only when its hash still matches. An unpublished private temporary copy may be discarded/recreated only after ownership and unchanged source are verified; unexpected content stays untouched and is reported. A monthly file matching the recorded after hash completes that publication; a matching before hash can receive the saved replacement. Anything else stops effects on the affected state for reconciliation. Repeated recovery cannot append twice or delete a changed original. Do not clear unresolved pending evidence.

This is recoverable progress, not whole-run rollback: earlier trip/month replacements can be visible when a later independent operation fails. File flush/replace and OS locking must be tested on Windows/Linux. Do not claim power-loss guarantees beyond verified filesystem behavior or automatically clear suspicious state.

## Per-run reporting and failure isolation

Write `report-<UTC timestamp>-<random token>.json` in the JSON folder, exclusively created for this invocation. Include report version, run identity, complete/incomplete status, counts and issue records with affected photo/item, issue and action. These timestamps identify a run, never a trip. Update the same report atomically as issues arise and finalize it after normal completion, interruption handling or a known stop. Recovered work receives a new run report; retain earlier reports.

Persist diagnostics independently of monthly/state success, including nonmatches as normal counts, individual skipped photos, unavailable readings when relevant, malformed durations, date exceptions, overlaps, clear conflicts, movement/publication and recovery errors. Reports contain necessary identity/action data and requested-field diagnostics only, never excluded dashboard OCR. If report writing fails, surface a sanitized stderr diagnostic and incomplete status without claiming a saved report; continue only effects that remain independently safe and verifiable. An unwritable shared output/state generally prevents further effects. Do not retry a global failure per photo indefinitely.

Shared-asset loss has its explicit run-stop/no-business-effects rule. A conflicting clear tie has its explicit preflight stop. All other unexpected failures use BRD R16's preserve/report/continue behavior at the smallest independently safe item/operation. A failed month/publication state can make multiple trips dependent; skip those until verified while unrelated verified work may proceed. Safe interruption handling preserves flushed pending state and reports where possible; abrupt termination can leave the last report incomplete and is reconciled by the next invocation.
