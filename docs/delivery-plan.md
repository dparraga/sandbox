# Integrated delivery plan

**Reviewed interpretation interface/schema and explicit failure, duration and date policies approved; application adoption still depends on artifact and validation gates.** This is the authoritative completion plan for [BRD R01-R16](BRD.md), constrained by [TRD](TRD.md). It consolidates the earlier broad processing proposals in [solution design](repository-structure.md); approved component contracts remain authoritative for their APIs. The user approved the two-delivery sequence and the confirmed policies recorded in the [BRD](BRD.md). Remaining batch identity/recovery mechanisms and unaudited artifact choices below remain proposals. Approval before implementation must identify accepted decisions and remaining blockers. Unchanged approved decisions persist across features; permission to plan is not permission to implement an unresolved policy.

## Starting point and delivery sequence

The installed Windows/Linux CLI currently exposes readiness, help/version and `discover SOURCE`. Discovery, original-capture metadata reading, strict fixed-offset timestamp conversion and bounded grouping are implemented. The per-field latest-clear candidate selector is implemented internally; it returns all equally latest clear indices and does not resolve values.

HEIC decoding, layout recognition, OCR/readability, the four requested readings, equal-time value resolution, monthly JSON and photo movement are absent from the application. Existing installed-package/container tests cover the existing components, not photo processing. Local evaluation decoded 16 positive examples on Windows and ran eight focused OCR regions across two previews/both layouts with successful exits and nonempty text. A focused human comparison found six of eight whole regions exact after whitespace normalization, with one title-token error and one MPG-unit error; this is not numeric accuracy certification or sixteen-photo coverage. Negative recognition, Linux decoding, end-to-end behavior and performance remain unverified. See [sample evidence and privacy limits](sample-evaluation.md).

The approved sequence uses two remaining features, each with one feature branch and integrated tests/docs. Decoder, OCR, schema and move helpers are implementation tasks inside these features, not additional standalone feature PRs.

## Processing design and interfaces

Reuse the package, standard-library CLI/JSON/filesystem facilities, ExifRead reader and pure APIs. Keep image/OCR effects separate from grouping and output effects; no database, service, GUI or general plugin framework is needed.

1. `discover_heic(source)` supplies candidate paths under its existing [contract](heic-discovery.md). A filename candidate is not a layout match.
2. An interpretation adapter accepts a candidate plus local decoder/OCR assets and returns a layout outcome and field observations. Decode/orient pixels once per image; preserve original bytes. Each field observation carries field identity, raw displayed text, clear/unclear/absent status and, where approved, parsed value/unit. Keep internal recognition/readability evidence separate from serialized trip output. A confirmed nonmatch is normal: leave it untouched and continue without requiring capture metadata. An absent or unreadable field on a recognized layout is also normal; retain an earlier clear value or emit null when none is clear. Neither outcome is an interpretation failure. Individual decode/OCR/resource execution failures leave the photo untouched, report and continue; unavailable shared assets stop the run incomplete before moves/monthly changes. Never classify an execution failure as a nonmatch.
3. Reuse `read_capture_metadata` and `parse_capture_time` unchanged. Capture time retains original date/time/offset and supported precision; dashboard clock is excluded from extraction and cannot supply trip date. Missing/invalid original timestamps on qualifying photos leave those photos untouched, add a report issue/action and continue; exclude them from grouping and output. There is no timestamp fallback.
4. Feed only qualified, policy-eligible observations into `group_capture_times`. Map each group's indices to its observations, then call `latest_clear_indices` separately for each of the four requested fields. Map group-local indices back to photo observations. The value layer preserves clear zero, emits JSON null for no candidates, uses a sole candidate, and applies the approved equal-time policy; input order never silently chooses a winner.
5. Build an in-memory output/move plan before effects. The plan associates one resolved entry with each trip, an approved month and destination filenames. Validate output/schema/conflicts under the approved policies before applying effects. Move only qualifying originals; nonmatches remain untouched. File and JSON operations must follow the approved failure/recovery contract; an atomic JSON replacement alone does not make a multi-file run transactional.

Proposed final command: `flex-photo process SOURCE --destination DESTINATION --json-output OUTPUT --window-seconds 180`, with explicit local OCR executable/model configuration where provisioning cannot supply fixed paths. Preserve existing `discover`, help/version and module entry point. Exact argument validation and diagnostic/exit semantics belong to feature 2's approved contract; document real behavior and do not add calibration options without sample evidence.

The approved dashboard scope is only trip distance (miles), trip duration (`hh:mm`), Trip Average MPG and odometer when present. The [monthly contract](monthly-json.md) owns the approved field names, exact decimal strings, literal units, nulls, equality and explicit trip-date derivation. Necessary layout anchors may be inspected for recognition; no other dashboard values, icons, colors, gauges or needles become observations, evidence fields or serialized output. Missing odometer or another unavailable reading cannot block extraction of available fields. Grouping retains the approved inclusive first-to-last default of three minutes without chaining.

Malformed duration is null at that photo, reported and excluded from clear candidates; an earlier valid duration remains eligible. Trip date uses the last capture's local date, or UTC date when the approved UTC-month exception applies. Equally latest captures on different local days within the same local month use the greatest local calendar date and report it. These policies and the concrete interpretation/schema contract are approved; exact artifact adoption still requires its evidence gates.

## Dependency, compatibility and offline gates

Recommend CPU-only Pillow plus a libheif-backed adapter and Tesseract 5 with one local English `tessdata_fast` model. Tesseract provides text/TSV output and local model selection; upstream model documentation requires its LSTM engine. This is a candidate stack, not proven dashboard recognition. Evaluate another OCR stack only if labeled results demonstrate a deficiency; do not provision two engines speculatively. Sources: [Tesseract CLI](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html), [model repository](https://github.com/tesseract-ocr/tessdata_fast).

Before adopting artifacts, record exact release/build/platform/architecture, source, SHA-256, native/transitive components, model commit/hash, licenses and exceptions, notices/source/relink obligations and current vulnerabilities. MIT applies to the application's own code and does not waive third-party obligations. Audit actual Windows DLLs/executables and Linux packages, including any redistributed container, rather than Python metadata alone. No candidate is approved for application adoption. The [interpretation contract](offline-photo-interpretation.md) distinguishes inspected payloads and actual Windows preview decoding from outstanding OCR accuracy, Linux and offline-validation gates; evaluation versions are not production pins.

The [offline interpretation proposal](offline-photo-interpretation.md#artifact-recommendation-and-safety-gates) owns current artifact recommendations and their security/license gates. Inspection found the discontinued pi-heif 1.4.0 Linux payload contains libheif 1.23.0, affected by a current HEVC decode advisory; do not adopt it without verified fixes. Pillow 13.0.0, maintained pillow-heif 1.8.1 and platform-specific Tesseract builds are audit candidates, not approved pins. The recommended deployment installs upstream wheels separately and distributes no native binaries; any future binary/container redistribution needs its separate compliance gate. The existing container is bookworm, whose Tesseract candidate is 5.3.0-2; trixie metadata does not validate it. Keep exact artifact hashes, payload inspection and execution evidence in ignored state; publish only selected reproducible setup after approval.

Validate the selected artifacts on supported CPython 3.13/3.14 and actual Windows architecture plus the Linux image. Pillow's [support matrix](https://pillow.readthedocs.io/en/stable/installation/python-support.html) alone does not establish HEIC/Tesseract compatibility. Any runtime/support-range change needs approval. Preserve existing pinned build practices and image digest; extend applicable package/container checks for the chosen assets.

Confirmed: installation and model download may use a one-time online setup; photo processing must then run offline. Provision assets separately; execution loads only local assets. Unavailable shared assets stop the run incomplete before any moves or monthly changes. Future setup must identify selected artifact hashes, local paths and offline verification commands; those commands remain provisional until artifacts and the process interface are selected. Verify the complete path with networking disabled, nonroot container execution, read-only application/root filesystem and explicit writable disposable output/temp mounts. Use subprocess argument arrays, bounded image/OCR resources and sanitized diagnostics; reject corrupt/oversized inputs under the approved batch policy. Pillow documents [decompression-bomb protections](https://pillow.readthedocs.io/en/stable/reference/Image.html); native HEIC behavior and process time/memory limits still need validation. Keep originals, labels, raw metadata and previews out of tracked files, packages, images, logs and CI artifacts. No external processing API or inference fee is proposed; local compute/storage, native-build work and CI usage remain costs. Docker Desktop is optional and is not universally free/open source.

## Incremental output and recovery

The user confirmed monthly append, skipping exact repeats, reporting overlaps, preserving completed work, safe resume and unexpected-error skip/report-or-log/continue; the [BRD](BRD.md) is authoritative. The identity, conflict-detection, state and effect-order mechanisms below remain **proposed**. Append new, disjoint trips to existing `YYYY-MM.json` files while preserving every existing entry's values and order. Do not reject a month merely because it exists. Reuse standard-library JSON, SHA-256 and filesystem operations; no database or framework is needed. Record trip membership privately rather than adding photo identifiers to the public field schema.

Recommend one private JSON sidecar in the output directory containing committed trip memberships (sets of original-byte SHA-256 hashes, capture instants, selected month and entry digest) and, only while a batch is pending, its source/destination paths and content hashes, complete planned monthly JSON contents, monthly before/after hashes and progress. Persist the plan before moving anything. This is necessary evidence for retrying after originals have moved; regenerating from the remaining source alone could lose readings or append a partial duplicate. A simpler output-only approach cannot reliably recognize retries or newly supplied photos without either adding provenance to the future public schema or requiring manual reconciliation after every interruption. Sidecar format, privacy and recovery behavior require approval; it is a private index and one pending operation record, not a generalized journal system.

Preflight reads all indexed trips, including neighboring months, before appending:

- Exactly matching membership hashes mean an already committed trip: do not append, rewrite its entry or move the repeated copies. Hash-identical input copies count once for proposed membership identity; retain/report extra copies without deleting them. This content deduplication is a proposed persistence policy, not an approved grouping change.
- Partial/shared membership, including a subset retry, skips the affected trips and reports the overlap for reconciliation. After removing exact repeats, rerun the existing approved grouping API on all persisted and new capture instants across months. Skip/report affected trips if a resulting group mixes new/indexed membership or changes any indexed trip's membership, including splitting or merging old groups. Thus old captures at minutes 2/5 plus new minute 1 require reconciliation at a three-minute window; old 0/3 plus new 4 may append as a separate trip. Do not silently extend or replace existing entries. This is repeat-run reconciliation using the approved partition, not a new classifier or dashboard trip-identity check. Reading/regrouping history costs memory and O(n log n) time; no workload limit or additional index is assumed.
- Append only trips outside those conflicts. Matching is supported only against intact sidecar provenance created by this process, using the same approved schema/grouping configuration. Missing/inconsistent provenance, changed monthly entries or incompatible configuration prevent effects on affected output/state; report/log the issue and continue only independently safe work; never infer identity from equal field values. Existing unindexed output needs explicit reconciliation, not automatic import.

Proposed effect order: acquire exclusive use of the output state; validate the complete batch and existing outputs; durably save its pending plan; move each original with verified copy-before-source-delete; then replace monthly JSON files with the planned complete contents; finally mark provenance committed and clear pending progress. Reserve collision names without overwrite. A source is deleted only after its destination's complete bytes match. An unexpected copy, deletion or write failure skips the affected operation and retains verified destinations, remaining originals and pending state; report/log the issue and continue independently safe work. Do not publish a completed trip whose required move/output effects remain incomplete. Earlier month replacements may already be visible; this is recoverable progress, not whole-batch rollback. Diagnostic report writes are independent of these business-output effects and must remain possible during preflight or recovery failures wherever the report folder is writable.

On restart, inspect and verify pending recovery before applying new effects to its output/state. Compare actual files with recorded hashes: an already published planned month is complete, an unchanged old month can receive its planned replacement, and unexpected content leaves that item untouched for resolution, with its issue/action reported or logged. Similarly verify existing destinations and remaining sources before resuming or completing deletions; never overwrite a changed file. Interrupted copies use temporary files and are reverified before publication. Repeated recovery must not duplicate entries or claim incomplete work completed. Skip recovery operations whose safety cannot be verified and continue independently safe work; retain their pending evidence. Concurrent writers and ambiguous stale ownership must be refused, not assumed safe. Exact platform durability and exclusive-use mechanics remain implementation validation gates.

Confirmed policies (authoritative requirements are in the BRD):

- Identical equally latest parsed value/unit ties collapse; conflicting clear ties stop preflight and report before moves/monthly changes. Equality follows the approved monthly schema. Unclear observations do not create clear-value conflicts.
- Use the last photo's metadata-local month; if equally latest photos name different local months, use the shared instant's UTC month and report the exception. Do not stop for this approved exception.
- `photo.HEIC` collisions allocate `photo-01.HEIC`, then `photo-02.HEIC`, expanding beyond two digits. Retain an already suffixed stem (`photo-01-01.HEIC`); never overwrite. Source, destination and JSON folders are separate and nonnested. Resolved-link/reparse validation and exclusive-use mechanics remain proposed implementation details.
- Append distinct trips, skip exact repeats without silently rewriting entries and report overlaps. Membership identity, subset/partition conflict isolation and private sidecar recovery remain proposals described above. An empty/no-match batch creates no monthly records or moves, but still has its run report.

Produce one report file per run in the JSON output folder, recording affected photo, issue and action. Keep it through reported preflight/processing failures where writing is possible; never discard it merely because monthly validation, moves or recovery fail. Propose creating it independently of monthly publication and updating that same run's file as issues arise; exact format, filename and persistence mechanics remain design work. If the folder cannot be written, surface the report-write failure clearly without claiming a report was saved. Report storage must respect the separate/nonnested-folder policy and private-photo handling.

Approved execution-failure policy: leave an individually failed decoder/OCR/resource photo untouched, report and continue independent photos. Missing/unavailable shared assets stop the run, report incomplete and prevent moves or monthly JSON changes. Validate required shared assets before processing and complete interpretation/preflight before effects; if a shared asset becomes unavailable during interpretation, stop before effects. BRD R16 remains the default for other unexpected item/operation failures. No unsafe/unverified write or deletion, overwrite, corruption, loss of completed work/pending evidence or false completion is permitted. Ordinary nonmatches and absent/unclear fields remain normal outcomes. Known rules remain: conflicting equally latest clear readings stop preflight/report; qualifying photos with missing/invalid timestamps remain untouched/report/continue; latest-month ties use UTC/report. Malformed duration excludes only that clear candidate; same-month date ties use greatest local date/report.

Independence must be established before continuing effects: trips sharing one monthly replacement or provenance/pending record cannot safely proceed through unverified shared state. Skip effects on that affected month/state until it is verified; other work can continue only if it does not depend on it. This is a safety limit, not a new per-month storage mechanism. Missing shared assets, unavailable output/report storage or other global failures may leave all remaining work unprocessable. Report/log where possible, preserve pending progress and finish without claiming completion or retrying indefinitely. A failed report write must be surfaced without claiming a saved report; exact diagnostic fallback remains design work.
