# Offline photo interpretation

**Implemented interface and policies; artifact-entry and recipe reviews passed.** This contract scopes the interpretation adapter in the [integrated delivery plan](delivery-plan.md), implementing BRD R03/R05/R12-R14 and supplying observations for R04/R06-R11/R15-R16. Existing discovery, metadata, capture-time, grouping and selection contracts remain unchanged. The [monthly JSON contract](monthly-json.md) owns field identifiers, scalar types and equality; private labels remain local.

## Delivery and boundary

Interpret one HEIC candidate locally: decode its primary image, apply orientation once, identify Trip Summary or Drive Info from displayed layout evidence, and extract only trip distance (miles), trip duration (`hh:mm`), Trip Average MPG and odometer independently. A supported dashboard layout qualifies; no separate Flex classifier, trip-identity test, cloud call or model training is proposed. Keep originals byte-identical. The adapter supplies an internal callable and installed-package tests; the batch component owns CLI orchestration, trip value resolution, reports, monthly JSON and moves.

Use one adapter module with ordinary immutable result records rather than a general OCR framework. Approved interface: `interpret_photo(path: Path, assets: InterpretationAssets) -> PhotoInterpretation`. Assets contain validated local executable/model locations and fixed adapter settings. Results contain layout outcome, field observations, original capture metadata or its existing error, and issue/action records. Keep identity and raw evidence internal; they are not monthly JSON. A caller can map clear statuses to the existing `latest_clear_indices` API without changing its contract.

| Result | Meaning and caller action |
| --- | --- |
| `trip_summary` / `drive_info` | Positive layout anchors and field geometry agree. Extract only the four requested readings, independently even if some are unclear or absent. Read original metadata through the existing reader. Missing/invalid capture time does not erase displayed observations; the batch component leaves this photo untouched, reports and excludes it from grouping. |
| `nonmatch` | Decoded content is confidently outside both supported layouts under a validated recognition rule. Leave untouched; no capture timestamp is required. |
| `unresolved` | Partial/ambiguous anchors, unsupported rendering, failed decode/OCR, resource rejection or another unexpected case. Preserve source and return affected photo and issue; apply the approved failure actions below. Never turn failure into nonmatch. |

Only `trip_distance`, `trip_duration`, `trip_average_mpg` and `odometer` may be field observations. No EV ratio, range, clock, temperature, speed, gear, indicator, symbol, gauge or other dashboard data may be extracted, retained as an observation or serialized. Necessary anchors may be inspected only for layout recognition. Limit retained crop/token evidence to requested readings and necessary anchors. Trip date is derived from existing original capture metadata under the [monthly contract](monthly-json.md), never OCR.

Each field observation contains `field_id`, `status` (`clear`, `unclear`, `absent`), optional `raw_text`, parsed value/unit only when clear, and local evidence such as crop bounds and OCR tokens. Diagnostics distinguish failed execution from ordinary unreadable fields. No OCR result may silently supply a value for a different field. A later absent/unclear observation does not override an earlier clear reading; clear zero remains clear. Unexpected Trip Time format yields null for that observation plus an issue while other fields proceed. Exclude a malformed duration from clear candidates, report it and keep an earlier valid duration eligible under the approved policy.

## Recognition and readability

Start with Tesseract English LSTM text/TSV plus layout-specific label and geometry rules. Use Pillow for orientation, cropping, grayscale/contrast and bounded resizing; NumPy, OpenCV, pytesseract, a second model and a trained classifier are unnecessary for the first evaluation. Invoke the executable with standard-library subprocess argument arrays. Use layout-specific bounded title/label anchor regions to locate the requested readings, then OCR only their bounded crops. Do not retain a full-dashboard OCR transcript or crop excluded regions merely to label them. Unknown positioning produces unresolved rather than wider indiscriminate extraction. Perspective correction or additional processing needs evidence that the simpler path fails; do not add a calibration interface speculatively.

For Trip Summary require the title and the associated summary labels/relative positions; for Drive Info require its title and associated distance/Trip Time geometry. A requested reading or unit alone never establishes the layout. Same-row ambiguous title candidates, incomplete anchors or unsupported geometry produce unresolved. Anchor tolerances and crop transforms are calibrated against the existing private samples, never loaded from their labels or identifiers at runtime. Sixteen positive examples cannot validate false-positive behavior. Exact uniform decoded images supply a narrow synthetic nonmatch rule; unknown content remains unresolved.

The bounded title search includes right-shifted titles. Filter short glyph groups using undilated connected components before OCR so a clock-shaped group does not displace the supported title. OCR only the upper surviving candidate; retain exact agreement across both title views and the literal label words in each requested-label view. Trailing punctuation at a label edge is allowed; letters, case and word spacing are not repaired, and extra adjacent alphanumeric text does not satisfy this punctuation-only rule. A better title candidate alone does not make unreadable labels qualify. Processing-recipe changes invalidate incompatible saved extraction checkpoints.

A human label is clear only when the complete token and its associated unit/field are unambiguous at native oriented resolution. Mark visible but clipped, obscured, conflicting or ambiguous tokens unclear. Mark absent only when the field is not displayed or not present in that layout; failure to recognize visible text is unclear. Do not label or interpret excluded dashboard content. The existing 16 positive previews are the starting evidence for focused four-reading expectations; additional user photos are not a new prerequisite. Missing odometer or another unavailable field cannot block independent extraction of the available readings.

Verify requested label words and geometry independently of the reading grammar. Locate consistent numeric glyph heights/baselines, separate numbers from units, preserve detached marks and antialiased strokes, and cap padding at the measured whitespace midpoint so neighboring glyphs do not cross into another token crop. Missing numeric/unit segmentation makes that field unclear; do not fall back to wider unrelated OCR. For segmented scalar readings, an omitted adjacent leading glyph/sign or bright ink continuing across the reading-crop boundary also makes the field unclear. Agreement among OCR views cannot validate a truncated numeric crop, and no missing digit or sign is inferred. Evidence records the actual reading bounds, including the narrower duration crop.

Use a fixed finite set of three numeric views and six unrestricted unit views. Numeric views use binary grayscale at 200/220 and native grayscale with Sauvola thresholding; the fixed character alphabet applies only to numeric crops. Unit views use grayscale Otsu and Sauvola at native/2x sizes plus two red-channel/component renders at 225/230. Dictionaries are disabled for numeric and unit crops; unit characters remain unrestricted, and case/tokens are never repaired or inferred. Settings are internal and fixed; no calibration CLI is introduced.

Automated clear requires complete same-field grammar and at least two distinct numeric views and two distinct unit views supporting the identical literal reading. Duration requires two distinct numeric views. Any conflicting complete reading anywhere in the fixed set vetoes clear, even if outvoted. Successfully executed invalid/empty views are unavailable evidence and do not vote; timeout, crash, resource or shared-asset failures retain the failure policies below. Cartesian combinations cannot count a single underlying view more than once. This is not confidence selection or majority voting.

Agreement is evidence, not proof: correlated views can repeat an incorrect reading. Compare actual outputs with private human expectations and report false-clear/false-unclear errors, coverage and runtime. The selected finite recipe is implemented; per-photo, integrated and platform evidence must identify the exercised installed source. No general accuracy threshold is asserted. If evaluation cannot reliably extract a field, disclose the limitation before claiming delivery; do not silently omit it or approve it through tests. Retain only validated requested-field/necessary-anchor evidence; omit rejected raw transcripts.

Numeric parsing uses exact decimal text and literal displayed units under the monthly contract, without float rounding or conversion. Duration uses hours:minutes; trip distance, Trip Average MPG and odometer remain separate observations. Retain only requested-field/necessary-anchor text privately so normalization is reviewable. Capture metadata and trip date never come from dashboard clock.

## Approved failure policy

Ordinary unreadable/absent individual fields remain normal: retain other available fields and earlier clear candidates, or null when none exist. Ordinary nonmatches remain untouched and processing continues. Qualifying photos with invalid/missing capture timestamps remain untouched, are reported and processing continues. Equally latest conflicting clear values stop preflight and are reported; identical parsed values with identical literal units collapse.

For an individual decoder/OCR crash, timeout or resource rejection, return unresolved, leave that photo untouched, report its issue/action and continue independent photos. An unreadable field is not a photo execution failure. If a shared executable/model is missing, invalid or unavailable, stop the run and report it incomplete; no moves or monthly JSON changes are allowed. Validate shared assets before processing and finish interpretation/preflight before effects, including a shared asset that becomes unavailable during processing. Preserve originals, earlier completed runs and pending recovery evidence. The adapter supplies these outcomes/diagnostics; the batch component owns report publication and effects.

## Artifact recommendation and safety gates

Research and artifact smoke evidence as of 2026-10-26 support Pillow 13.0.0, pillow-heif 1.8.1 and platform Tesseract builds with one hash-pinned English model for the approved adapter. The security/path and platform evidence below supports implementation after independent gate Review; complete readability and application acceptance remain implementation work. [Pillow 13.0.0 release notes](https://pillow.readthedocs.io/en/stable/releasenotes/13.0.0.html) include significant decoder/security fixes, so historical Pillow 12.0.0 research is not a production recommendation. Pillow is needed here for pixel processing even though standalone decoder data access exists. Avoid Arrow export; its [alignment advisory](https://github.com/python-pillow/Pillow/security/advisories/GHSA-654x-cwwv-5j9c) includes 13.0.0 and has no published patch. Read candidate files only through an explicit HEIF decoder, never unrestricted format sniffing; unrelated Pillow codecs are not processing paths.

The existing decoder-only [pi-heif 1.4.0](https://pypi.org/project/pi-heif/1.4.0/) is the first artifact to inspect because it avoids unnecessary encoding dependencies. However, upstream now [discontinues pi-heif at 1.4.0](https://pypi.org/project/pillow-heif/), and its [tagged build source](https://raw.githubusercontent.com/bigcat88/pillow_heif/v1.4.0/libheif/build_libs.py) references libheif 1.23.0. [GHSA-vv35-6hxg-95x8](https://github.com/strukturag/libheif/security/advisories/GHSA-vv35-6hxg-95x8) affects libheif through 1.23.5, including HEVC/grid decode paths, and is patched in 1.23.6. Decoder-only functionality does not exclude that defect. The isolated Windows version probe confirms pi 1.4.0 loads libheif 1.23.0 and libde265 1.1.1; inspected Linux payload also names libheif 1.23.0. Reject these current decoder-only wheels for adoption without verified fixes. Do not compensate by disabling security limits or merely limiting decoded dimensions.

Recommend the maintained published pillow-heif 1.8.1 for separately provisioned local deployment, subject to security/platform/readability gates. Its [bundled notice](https://raw.githubusercontent.com/bigcat88/pillow_heif/v1.8.1/LICENSES_bundled.txt) names libheif 1.23.6, libde265 1.1.3 and x265 4.3; Windows runtime reports x265 `4.3+1-e9b8812`. The [actual x265 revision header](https://raw.githubusercontent.com/Multicorewareinc/x265/e9b8812/source/x265.h) grants GPLv2 or later. [libheif](https://raw.githubusercontent.com/strukturag/libheif/v1.23.6/COPYING) and [libde265](https://raw.githubusercontent.com/strukturag/libde265/v1.1.3/COPYING) use LGPLv3, which incorporates GPLv3. A GPLv3-compatible combination is therefore a viable compliance route; the publisher's GPLv2 wheel notice alone does not establish complete binary redistribution compliance. Preserve original notices and each component's grants; do not relabel them MIT.

For this feature, recommend distributing the project's MIT source/wheel and source Dockerfile, with users obtaining hash-pinned upstream native wheels/OCR/model assets during one-time setup. Do not include a native wheelhouse, portable native bundle or prebuilt container in our distribution. Local installation/testing is separate from conveying those binaries; the [GPLv3 terms](https://raw.githubusercontent.com/strukturag/libheif/v1.23.6/COPYING) permit private execution without source-conveyance requirements. This deployment recommendation avoids a custom native build and retains upstream update support; it does not clear security or platform gates or waive downstream obligations if someone redistributes their combined installation.

If binary/container redistribution is later required, supply all original license/copyright/notice texts, applicable GPLv3/LGPLv3 terms, exact corresponding sources and build/patch scripts for the conveyed native payload (including actual x265 revision `e9b8812`, not merely release 4.3), and installation/replacement instructions. Keep own MIT sources available and permit replacement of interface-compatible shared libraries; do not lock their hashes in normal application execution so tightly that users cannot install an intentionally modified local library. Model integrity against untrusted bytes remains separate. The [tagged upstream build script](https://raw.githubusercontent.com/bigcat88/pillow_heif/v1.8.1/libheif/build_libs.py) identifies source releases but is not complete proof of the Windows toolchain/patch closure. No complete redistribution source bundle has been assembled or verified. That optional packaging would require a new concrete compliance assessment, rather than treating download links alone as corresponding-source delivery. A decoder-only custom build is unnecessary unless the published artifact fails a required security/runtime gate; it would add native toolchain, reproducibility and maintenance work and requires explicit approval of that material change.

OCR audit candidates are [Windows Tesseract 5.5.3.20260724](https://github.com/tesseract-ocr/tesseract/releases/expanded_assets/5.5.3) and the existing bookworm image's [Tesseract 5.3.0-2](https://packages.debian.org/bookworm/tesseract-ocr). They are different engines/builds and both require testing, not assumed output equivalence. Use the same [tessdata_fast 4.1.0 English LSTM model](https://github.com/tesseract-ocr/tessdata_fast/tree/4.1.0), resolved to commit `65727574dfcd264acbb0c3e07860e4e9e9b22185`; downloaded `eng.traineddata` is 4,113,088 bytes with SHA-256 `7d4322bd2a7749724879683fc3912cb542f19906c83bcc1a52132556427170b2`. The pinned model loaded successfully in the bounded Windows OCR probe described below. The 26,573,224-byte official Windows installer was downloaded and its published SHA-256 verified; it was extracted with a separately verified portable 7-Zip without executing the installer. All 139 extracted files were inventoried and hashed; native closure/security/source obligations remain unaudited. Authenticode returned `UnknownError` with a University of Mannheim signer, so signature trust is not established. Engine/model licenses are Apache-2.0; installer and Debian native closures have separate obligations. Do not assume distro/installer English data equals the selected model.

These engine versions have known [current advisories](https://github.com/tesseract-ocr/tesseract/security/advisories); [Debian's tracker](https://security-tracker.debian.org/tracker/source-package/tesseract) still lists bookworm vulnerabilities. Restrict model/config inputs to audited local assets, verify hashes before loading, use OEM 1 and text/TSV only, and pass only locally generated bounded PPM pixels to the engine. Never accept photo-controlled model/config paths, remote URLs, adaptation files or PAGE rendering. The [crafted-model recoder issue](https://github.com/tesseract-ocr/tesseract/security/advisories/GHSA-pqc9-gv83-r5mf) depends on malicious model bytes; the [PAGE ownership issue](https://github.com/tesseract-ocr/tesseract/security/advisories/GHSA-vf7v-2h4f-6f4j) is renderer-specific. Those restrictions exclude their described trigger paths, not every potential engine/native defect. Review exact native dependency versions and all applicable advisories before adoption.

### Candidate execution-path assessment

The inspected Windows full wheel reports only the libde265 1.1.3 decoder; libheif is 1.23.6. Its [security release](https://github.com/strukturag/libheif/releases/tag/v1.23.6) fixes the relevant HEVC bit-depth/grid/overlay issue and also documents a closed-form fix for the experimental uncompressed-codec CPU advisory, despite that advisory's stale empty patched-version field. Do not require an unspecified future patch for this candidate. Retain finite worker time/memory limits and decoder defaults; the hosted Linux probes now confirm the same native version/decoder list.

libde265 1.1.3 meets the fixed releases for the listed HEVC memory/lifetime defects. Two older advisories have empty patched-version fields: upstream [1.1.3 NAL source](https://raw.githubusercontent.com/strukturag/libde265/v1.1.3/libde265/nal-parser.cc) has geometric growth and linear stuffing-byte compaction for [GHSA-x27c](https://github.com/strukturag/libde265/security/advisories/GHSA-x27c-jp65-g395); its [image allocation source](https://raw.githubusercontent.com/strukturag/libde265/v1.1.3/libde265/image.cc) explicitly uses wide allocation arithmetic for [GHSA-vv8h](https://github.com/strukturag/libde265/security/advisories/GHSA-vv8h-932h-7r86). These source checks resolve the specific stale-metadata gaps, rather than asserting all native code is defect-free.

For OCR, the exercised inputs are generated PPM pixels and the immutable trusted English LSTM model; outputs are text/TSV. Current [Tesseract advisories](https://github.com/tesseract-ocr/tesseract/security/advisories) describe crafted model dimensions/recoder data, legacy model/adaptation initialization and PAGE rendering. Hash-verified model bytes, OEM 1, no external configurations/adaptation and no PAGE output exclude those described triggers. JPEG/TIFF/WebP/OpenJPEG loaders, archive extraction and curl URLs are outside this application path; do not pass original files, URLs or user-controlled configs to Tesseract. Leptonica's [1.87.0 PNM reader](https://raw.githubusercontent.com/DanBloomberg/leptonica/1.87.0/src/pnmio.c) handles our generated uncompressed crops. This is a scoped path assessment, not a complete vulnerability audit of every installer utility/DLL. Actual Linux engine/native versions and restricted synthetic offline execution are recorded below; complete application asset loading remains an implementation check; speculative unused-library closure is not an indefinite adoption gate for separately provisioned local deployment.

Keep decoder security defaults enabled; convert Pillow decompression warnings into rejection rather than suppressing them. Use one serial native worker with a 16-million-primary-pixel guard, bounded crops and initially a 1 GiB Windows aggregate job-memory limit or 1 GiB Linux address-space limit per worker/child process. Initial engineering limits are 30 seconds for decode/orientation, 15 seconds per OCR call and 120 seconds per photo. Enforce those bounds with a Windows kill-on-close Job Object or inherited Linux address-space limits before native work; Linux per-process limits do not establish an aggregate job limit. Process decode/OCR serially; the restricted container supplies an additional 1 GiB aggregate limit. terminate/reap native children on timeout. A parent timeout alone does not bound memory. Validate these guards on all 4032-by-3024 samples and forced failures during implementation; they are adjustable resource guards, not speed/memory targets or a claim of support for unseen oversized images. Failure to establish required enforcement must be surfaced before untrusted native execution.

Apply the fixed recognition recipe above only to bounded requested-reading/anchor crops, with OEM 1 and region-specific line/word segmentation. Limit a native crop to four million pixels and each rendered view to sixteen million. Preserve the existing serial worker, memory and deadline guards as view count increases. No originals are rewritten. The parent owns private workspace cleanup after worker/descendant teardown; bounded Windows sharing-violation retries do not suppress persistent or unrelated errors.

## Acceptance and approval

Validation separates native compatibility probes from application acceptance. Private application checks use the existing 16 positive photos and focused human expectations; public fixtures cover controlled mechanics and failures. Preserve original/copy/manifest bytes and keep private evidence local. See [sample coverage](sample-evaluation.md) and the [testing plan](testing-plan.md). Positive-only checks do not establish real nonmatch, unseen-layout or general glare accuracy; the authored monthly example is not measured OCR evidence.

[CI run 40284510596](https://github.com/dparraga/sandbox/actions/runs/40284510596) passed all ten jobs at commit `1b61c7a`. Four hash-pinned Windows/Linux CPython 3.13/3.14 probes imported Pillow 13.0.0 and pillow-heif 1.8.1, confirmed libheif 1.23.6 with only listed decoder libde265 1.1.3, and decoded the generated 64-by-64 HEVC white fixture correctly. Windows 3.13/3.14 also returned exact synthetic `HELLO` with the pinned model and Tesseract 5.5.3.20260724/Leptonica 1.87.0 while active outbound-block rules covered the audit/base Python and OCR executables. This is process-specific egress blocking, not whole-machine isolation.

The digest-pinned bookworm Python 3.13 candidate container decoded the same HEVC fixture and returned `HELLO` under `--network none`, nonroot, read-only root, dropped capabilities and a 1 GiB outer memory limit. The installed package inventory records Tesseract/libtesseract5 `5.3.0-2` and liblept5 `1.82.0-3+b3`; the engine reports Leptonica 1.82.0. Standalone Ubuntu 3.13/3.14 probes exercised decoding without OCR; the OCR engine is an external subprocess rather than a Python ABI module. These results establish scoped artifact compatibility/offline smoke evidence, not dashboard recognition, complete resource enforcement or all-platform installed application acceptance. The [Debian Leptonica tracker](https://security-tracker.debian.org/tracker/source-package/leptonlib) lists its tracked issues as resolved; generated PPM and the trusted model remain the scoped OCR paths.

Exact candidate names/hashes are in the checked-in audit manifest; runtime/native inventories, model identity and execution results are preserved in the CI reports and ignored state. One-time provisioning may use networking; subsequent processing must use only local assets. Missing shared assets follow the approved stop/incomplete policy. Never include private photos, labels or previews in a wheel, image, repository or public CI artifact.
