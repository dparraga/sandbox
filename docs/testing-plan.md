# Testing plan

Automation covers installed CLI/packaging, discovery, metadata/time/grouping/selection, native interpretation mechanics and authored batch scenarios. Private evaluation separately compares actual OCR against the existing 16 positive samples. Per-photo reading checks and real CLI monthly/movement/repeat checks complement the authored failure cases; neither replaces the other. Keep actual results, platform skips, failures and reviewed source identity in the feature PR and ignored local state. Component contracts own their acceptance rules; use [setup](bootstrap.md) for commands and [automation](github-test-automation.md) for CI.

Testing owns cases, fixtures, automation, execution, and results. After explicit implementation approval, Testing develops cases in parallel with Implementation and runs applicable tests as soon as code is runnable. Documentation records verified commands; Review independently checks coverage and findings; Lead validates evidence.

## Implemented acceptance coverage

Unit tests exercise readiness/help/version and argument errors. Integration tests execute installed module and console commands from an isolated path containing spaces/Unicode, verify exit/stdout/stderr semantics, wheel metadata/payload and no created files. Performance automation times repeated installed-process startup after warmup and records environment and sample counts; no speed threshold is approved. Container smoke checks exercise the installed CLI with network disabled, read-only filesystem and nonroot execution. Discovery tests additionally cover the approved traversal, inventory and failure contract. Metadata tests exercise original-capture text fidelity, missing values, sanitized errors, parser guards and file-handling failures. Installed-library integration runs outside the checkout with network calls blocked and checks source preservation. Container checks exercise extraction, capture-time conversion, grouping, a guard failure and dependency version/license retention using public metadata-only fixtures. Capture-time unit checks cover strict syntax, dates, offsets, fractional precision, sanitized errors and unchanged input; installed integration composes the reader with conversion. Grouping unit checks cover ordering, bounded windows, date/offset extremes and sanitized validation; installed integration composes metadata reading, conversion and grouping while preserving synthetic source bytes. These fixtures establish no image decodability or OCR accuracy.

## Artifact evidence and adapter acceptance

The candidate harness verifies exact artifact/model hashes, expected native versions and codec inventory, a public authored white HEVC decode and synthetic text OCR. Provisioning and restricted-container checks are separate from application tests. They support the scoped artifact adoption decision; they do not establish adapter recognition, field correctness or full application offline composition. Keep actual CI run/head evidence in the PR and ignored state.

Private worker expectations cover 48 clear and 16 absent readings across the existing 16 positive photos. Use them for acceptance comparison after code is runnable; independently check expectations where practical. Runtime code must not consume private labels/ROIs or choose behavior by sample name/hash. Two native-resolution error-region refinements are bounded observations, not a general preprocessing or readability policy. No new user photos are required before implementation.

Interpretation tests distinguish mocked observation grammar from actual worker execution. Native checks cover shared assets, corrupt/blank fixture preservation, deadlines/reaping, Windows aggregate Job Object memory and descendant cleanup, and Linux address-space enforcement. Batch tests use authored observations with real disposable filesystem effects for exact values/date/month rules, independent selection, no-overwrite collisions, repeats/overlaps, external edits, locking, partial movement/publication and repeated recovery. These tests do not establish dashboard accuracy. The restricted container runs applicable installed interpretation and batch tests with local assets; private originals never become move fixtures.

## Reliability validation

Exercise graceful pause after a completed photo, explicit resume without repeated OCR, changed input/configuration, retained failures, unexpected termination with a torn last append, repeated recovery and partial moves/monthly publication. Test monotonic cumulative timing with long offline gaps and reused results; verify progress counts, ETA availability, refresh/fallback frequency and bounded opt-in diagnostic retention. Inject post-publication temporary cleanup failures and report filesystem/serialization errors; verify on-disk identity, useful item reports, aggregate counts and suppression of repetitive console errors. Preserve the 16 MP guard and strict recognition/metadata policies. Actual Windows/Linux, installed-process and private-photo outcomes remain separate evidence.

## Sparse output and capture fallback validation

Test legacy-to-sparse conversion with all-unavailable fields, zero/duration zero, preserved non-null values/order/membership and updated private digests. Inject interruption after journal/month/state publication, restart in another process, repeat conversion, reject edited or unreachable snapshots, and preserve exact legacy pending plans. Preflight conflicts or shared-asset loss must not trigger automatic conversion.

Test metadata/creation/filename precedence, invalid surviving metadata, true birth-time availability without ctime/mtime substitution, exact filename milliseconds and first-to-last grouping, pinned Los Angeles day/DST boundaries, invalid/ambiguous/nonexistent local clocks, and silent bare-date skips. Revalidate changed birth time without repeating OCR and before source deletion; reject inconsistent saved capture contexts. Verify installed Windows/Linux and restricted-container paths separately from private OCR readability. Planned checks are not passed evidence.

## Integrated acceptance and performance

- Unit: tied-value resolution, four-reading-only serialization, exact decimal/literal-unit equality, clear zero/null and approved capture-bound arrays/date rules; internal candidate selection is covered separately. Cover latest-date ties within one local month without silently moving the date to a previous UTC month, and the separate approved differing-local-month exception.
- Integration: folder scan through recognition, metadata extraction, grouping, movement, and monthly JSON output on disposable fixture trees; compare file inventories and approved JSON expectations.
- Performance: measure end-to-end processing and useful stage timings, throughput, memory, and workload size. Use the confirmed representative workload of 500-1,000 photos, approximately 300 matching, on Windows with 32 GB RAM and an Intel Core Ultra 9 288V where available. Record actual photo count, dimensions, nesting, hardware, OS/container resources, runtime/model versions, cold versus warm setup, and repetitions; disclose substitutions. Propose limits only after representative measurements and user approval; no limits or coverage targets are currently set.

Use the [sample handling rules and coverage limits](sample-evaluation.md) for originals, hashes, disposable copies, pending labels and publication authorization. Synthetic filesystem and metadata-only fixtures do not establish image decodability or OCR accuracy. Validate capture metadata against the existing original-capture evidence using disposable private sample copies; publish only aggregate results, never raw metadata.

## Decisions needed before affected tests

The [BRD](BRD.md) and approved component/batch contracts are authoritative. Preserve timestamp exclusions, suffixes, folder separation, date/month exceptions, units, per-run reports, malformed-duration earlier-value retention and shared-asset stop/incomplete/no-effects behavior. Test saved-state schema and capture/membership invariants before recovery effects, edited monthly output before source movement, before/after publication identity, preserved unexpected temporary bytes and safe fresh-copy recovery. Do not encode unapproved policies or claim positive-only samples establish broad negative recognition.

Before an implementation PR, run applicable local tests and independently review fixes. On PR updates, rerun affected tests and review corrections before pushing. Preserve commands, environment, results, failures, and remaining gaps in the feature's ignored local state; publish only suitable sanitized evidence.
