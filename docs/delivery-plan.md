## Processing design and interfaces

Reuse the package, standard-library CLI/JSON/filesystem facilities, ExifRead reader and pure APIs. Keep image/OCR effects separate from grouping and output effects; no database, service, GUI or general plugin framework is needed.

1. `discover_heic(source)` supplies candidate paths under its existing [contract](heic-discovery.md). A filename candidate is not a layout match.
2. An interpretation adapter accepts a candidate plus local decoder/OCR assets and returns a layout outcome and field observations. Decode/orient pixels once per image; preserve original bytes. Each field observation carries field identity, raw displayed text, clear/unclear/absent status and, where approved, parsed value/unit. Keep internal recognition/readability evidence separate from serialized trip output. A confirmed nonmatch is normal: leave it untouched and continue without requiring capture metadata. An absent or unreadable field on a recognized layout is also normal; retain an earlier clear value or emit null when none is clear. Neither outcome is an interpretation failure. A decode/execution failure or unresolved layout classification is distinct; proposed batch stops are listed below.
3. Reuse `read_capture_metadata` and `parse_capture_time` unchanged. Capture time retains original date/time/offset and supported precision; dashboard clock is its own displayed field. Missing/invalid original timestamps on qualifying photos leave those photos untouched, add a report issue/action and continue; exclude them from grouping and output. There is no timestamp fallback.
4. Feed only qualified, policy-eligible observations into `group_capture_times`. Map each group's indices to its observations, then call `latest_clear_indices` separately for every inventoried field. Map group-local indices back to photo observations. The value layer preserves clear zero, emits JSON null for no candidates, uses a sole candidate, and applies the approved equal-time policy; input order never silently chooses a winner.
5. Build an in-memory output/move plan before effects. The plan associates one resolved entry with each trip, an approved month and destination filenames. Validate output/schema/conflicts under the approved policies before applying effects. Move only qualifying originals; nonmatches remain untouched. File and JSON operations must follow the approved failure/recovery contract; an atomic JSON replacement alone does not make a multi-file run transactional.

Proposed final command: `flex-photo process SOURCE --destination DESTINATION --json-output OUTPUT --window-seconds 180`, with explicit local OCR executable/model configuration where provisioning cannot supply fixed paths. Preserve existing `discover`, help/version and module entry point. Exact argument validation and diagnostic/exit semantics belong to feature 2's approved contract; document real behavior and do not add calibration options without sample evidence.

The interpretation field inventory must cover distance, `hh:mm` duration, EV ratio, average MPG, odometer, range and dashboard clock, plus all other available displayed fields in the supplied layouts. Samples also show ambient temperature, speed, gear and indicators; human labeling must distinguish readable values, symbols and absence. The seven original metrics are not an exhaustive schema. No additional Flex/trip identity classifier is required. Grouping retains the approved inclusive first-to-last default of three minutes; consecutive gaps cannot extend it.

Preserve displayed units without conversion. An unexpected duration format yields null for that field, is reported and allows other fields to continue. The final schema/example must expose the interaction with an earlier clear duration if such a case occurs; neither force a trip-wide null nor treat the exceptional reading as ordinary absence without resolving that material ambiguity. Ordinary absent/unclear fields retain the approved earlier-clear/null rules.

## Incremental output and recovery

The user confirmed monthly append, skipping exact repeats, reporting overlaps, preserving completed work and safe resume; the [BRD](BRD.md) is authoritative. The identity, conflict-detection, state and effect-order mechanisms below remain **proposed**. Append new, disjoint trips to existing `YYYY-MM.json` files while preserving every existing entry's values and order. Do not reject a month merely because it exists. Reuse standard-library JSON, SHA-256 and filesystem operations; no database or framework is needed. Record trip membership privately rather than adding photo identifiers to the public field schema.

Recommend one private JSON sidecar in the output directory containing committed trip memberships (sets of original-byte SHA-256 hashes, capture instants, selected month and entry digest) and, only while a batch is pending, its source/destination paths and content hashes, complete planned monthly JSON contents, monthly before/after hashes and progress. Persist the plan before moving anything. This is necessary evidence for retrying after originals have moved; regenerating from the remaining source alone could lose readings or append a partial duplicate. A simpler output-only approach cannot reliably recognize retries or newly supplied photos without either adding provenance to the future public schema or requiring manual reconciliation after every interruption. Sidecar format, privacy and recovery behavior require approval; it is a private index and one pending operation record, not a generalized journal system.

Preflight reads all indexed trips, including neighboring months, before appending:

- Exactly matching membership hashes mean an already committed trip: do not append, rewrite its entry or move the repeated copies. Hash-identical input copies count once for proposed membership identity; retain/report extra copies without deleting them. This content deduplication is a proposed persistence policy, not an approved grouping change.
- Partial/shared membership, including a subset retry, stops and reports the overlap for reconciliation. After removing exact repeats, rerun the existing approved grouping API on all persisted and new capture instants across months. Stop if a resulting group mixes new/indexed membership or changes any indexed trip's membership, including splitting or merging old groups. Thus old captures at minutes 2/5 plus new minute 1 stop at a three-minute window; old 0/3 plus new 4 may append as a separate trip. Do not silently extend or replace existing entries. This is repeat-run reconciliation using the approved partition, not a new classifier or dashboard trip-identity check. Reading/regrouping history costs memory and O(n log n) time; no workload limit or additional index is assumed.
- Append only trips outside those conflicts. Matching is supported only against intact sidecar provenance created by this process, using the same approved schema/grouping configuration. Missing/inconsistent provenance, changed monthly entries or incompatible configuration stop before effects; never infer identity from equal field values. Existing unindexed output needs explicit reconciliation, not automatic import.

Proposed effect order: acquire exclusive use of the output state; validate the complete batch and existing outputs; durably save its pending plan; move each original with verified copy-before-source-delete; then replace monthly JSON files with the planned complete contents; finally mark provenance committed and clear pending progress. Reserve collision names without overwrite. A source is deleted only after its destination's complete bytes match. Any copy, deletion or write failure stops further work and retains verified destinations, remaining originals and pending state. Earlier month replacements may already be visible; this is recoverable progress, not whole-batch rollback. Diagnostic report writes are independent of these business-output effects and must remain possible during preflight or recovery failures wherever the report folder is writable.

On restart, recover the pending plan before discovering new work. Compare actual files with recorded hashes: an already published planned month is complete, an unchanged old month can receive its planned replacement, and any unexpected content stops for resolution. Similarly verify existing destinations and remaining sources before resuming or completing deletions; never overwrite a changed file. Interrupted copies use temporary files and are reverified before publication. Repeated recovery must finish the same entries exactly once. Concurrent writers and ambiguous stale ownership must be refused, not assumed safe. Exact platform durability and exclusive-use mechanics remain implementation validation gates.

Confirmed policies (authoritative requirements are in the BRD):

- Identical equally latest parsed value/unit ties collapse; conflicting clear ties stop preflight and report before moves/monthly changes. The exact equality representation awaits the schema. Unclear observations do not create clear-value conflicts.
- Use the last photo's metadata-local month; if equally latest photos name different local months, use the shared instant's UTC month and report the exception. Do not stop for this approved exception.
- `photo.HEIC` collisions allocate `photo-01.HEIC`, then `photo-02.HEIC`, expanding beyond two digits. Retain an already suffixed stem (`photo-01-01.HEIC`); never overwrite. Source, destination and JSON folders are separate and nonnested. Resolved-link/reparse validation and exclusive-use mechanics remain proposed implementation details.
- Append distinct trips, skip exact repeats without silently rewriting entries and report overlaps. Membership identity, subset/partition conflict stops and private sidecar recovery remain proposals described above. An empty/no-match batch creates no monthly records or moves, but still has its run report.

Produce one report file per run in the JSON output folder, recording affected photo, issue and action. Keep it through reported preflight/processing failures where writing is possible; never discard it merely because monthly validation, moves or recovery fail. Propose creating it independently of monthly publication and updating that same run's file as issues arise; exact format, filename and persistence mechanics remain design work. If the folder cannot be written, surface the report-write failure clearly without claiming a report was saved. Report storage must respect the separate/nonnested-folder policy and private-photo handling.

The proposed combined preflight contract includes confirmed conflicting-reading stops/overlap reports and these still-unapproved additional stops: unavailable required local decoder/OCR assets; decode/resource-limit or OCR execution failure; unresolved layout classification; unsupported clear value representation/schema other than the approved duration exception; unsafe paths or inability to reserve output; invalid/inconsistent existing JSON/provenance, duplicate/overlap conflicts or pending recovery mismatch. Separate/nonnested folders and no overwrite are confirmed constraints. Missing/invalid qualifying timestamps skip untouched/report/continue; latest-month ties use UTC/report; unexpected duration yields field null/report/continue. Ordinary nonmatches continue; unreadable/absent fields follow earlier-clear/null rules. Write, copy, deletion and durability failures after effects begin use the proposed recovery behavior above. Reporting remains available through stops where writing is possible. No metadata fallback or fabricated field value is allowed.
