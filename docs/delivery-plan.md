## Processing design and interfaces

Reuse the package, standard-library CLI/JSON/filesystem facilities, ExifRead reader and pure APIs. Keep image/OCR effects separate from grouping and output effects; no database, service, GUI or general plugin framework is needed.

1. `discover_heic(source)` supplies candidate paths under its existing [contract](heic-discovery.md). A filename candidate is not a layout match.
2. An interpretation adapter accepts a candidate plus local decoder/OCR assets and returns a layout outcome and field observations. Decode/orient pixels once per image; preserve original bytes. Each field observation carries field identity, raw displayed text, clear/unclear/absent status and, where approved, parsed value/unit. Keep internal recognition/readability evidence separate from serialized trip output. A confirmed nonmatch is normal: leave it untouched and continue without requiring capture metadata. An absent or unreadable field on a recognized layout is also normal; retain an earlier clear value or emit null when none is clear. Neither outcome is an interpretation failure. A decode/execution failure or unresolved layout classification is distinct; proposed batch stops are listed below.
3. Reuse `read_capture_metadata` and `parse_capture_time` unchanged. Capture time retains original date/time/offset and supported precision; dashboard clock is its own displayed field. There is no timestamp fallback.
4. Feed only qualified, policy-eligible observations into `group_capture_times`. Map each group's indices to its observations, then call `latest_clear_indices` separately for every inventoried field. Map group-local indices back to photo observations. The value layer preserves clear zero, emits JSON null for no candidates, uses a sole candidate, and applies the approved equal-time policy; input order never silently chooses a winner.
5. Build an in-memory output/move plan before effects. The plan associates one resolved entry with each trip, an approved month and destination filenames. Validate output/schema/conflicts under the approved policies before applying effects. Move only qualifying originals; nonmatches remain untouched. File and JSON operations must follow the approved failure/recovery contract; an atomic JSON replacement alone does not make a multi-file run transactional.

Proposed final command: `flex-photo process SOURCE --destination DESTINATION --json-output OUTPUT --window-seconds 180`, with explicit local OCR executable/model configuration where provisioning cannot supply fixed paths. Preserve existing `discover`, help/version and module entry point. Exact argument validation and diagnostic/exit semantics belong to feature 2's approved contract; document real behavior and do not add calibration options without sample evidence.

The interpretation field inventory must cover distance, `hh:mm` duration, EV ratio, average MPG, odometer, range and dashboard clock, plus all other available displayed fields in the supplied layouts. Samples also show ambient temperature, speed, gear and indicators; human labeling must distinguish readable values, symbols and absence. The seven original metrics are not an exhaustive schema. No additional Flex/trip identity classifier is required. Grouping retains the approved inclusive first-to-last default of three minutes; consecutive gaps cannot extend it.

## Dependency, compatibility and offline gates

Recommend CPU-only Pillow plus a libheif-backed adapter and Tesseract 5 with one local English `tessdata_fast` model. Tesseract provides text/TSV output and local model selection; upstream model documentation requires its LSTM engine. This is a candidate stack, not proven dashboard recognition. Evaluate another OCR stack only if labeled results demonstrate a deficiency; do not provision two engines speculatively. Sources: [Tesseract CLI](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html), [model repository](https://github.com/tesseract-ocr/tessdata_fast).

Before adopting artifacts, record exact release/build/platform/architecture, retrieval source, SHA-256, direct/transitive/native components, model commit/hash, licenses with exception qualifiers, notices/source/relink obligations and compatibility with the project's retained Apache-2.0 license. Audit Windows executables/DLLs and Linux/container packages, not merely Python metadata. Verify current vulnerabilities and mitigations for those artifacts. The temporary sample-evaluation versions are evidence only, not production pins.

Stock pillow-heif wheels need particular review: upstream bundled notices identify GPLv2 wheels, LGPLv3 libheif/libde265, GPLv2 x265 and Windows GCC runtime exceptions. The adapter source's BSD license does not describe the full wheel. Prefer a decoder-only native build if feasible and materially simpler to distribute compliantly; prove its Windows/Linux packaging before selecting it. A license change does not automatically cure incompatibility or codec distribution questions. Upstream documentation describes source builds and warns Windows builds are difficult; its `latest` page currently describes a development version, so pin from verified releases, not that page. Sources: [bundled notices](https://raw.githubusercontent.com/bigcat88/pillow_heif/master/LICENSES_bundled.txt), [installation](https://pillow-heif.readthedocs.io/en/latest/installation.html).

Validate the selected artifacts on supported CPython 3.13/3.14 and actual Windows architecture plus the Linux image. Pillow's [support matrix](https://pillow.readthedocs.io/en/stable/installation/python-support.html) alone does not establish HEIC/Tesseract compatibility. Any runtime/support-range change needs approval. Preserve existing pinned build practices and image digest; extend applicable package/container checks for the chosen assets.

Provision assets separately; execution loads only local assets and fails clearly if required assets are missing. Verify the complete path with networking disabled, nonroot container execution, read-only application/root filesystem and explicit writable disposable output/temp mounts. Use subprocess argument arrays, bounded image/OCR resources and sanitized diagnostics; reject corrupt/oversized inputs under the approved batch policy. Pillow documents [decompression-bomb protections](https://pillow.readthedocs.io/en/stable/reference/Image.html); native HEIC behavior and process time/memory limits still need validation. Keep originals, labels, raw metadata and previews out of tracked files, packages, images, logs and CI artifacts. No external processing API or inference fee is proposed; local compute/storage, native-build work and CI usage remain costs. Docker Desktop is optional and is not universally free/open source.

## Proposed incremental output and recovery

This policy is **unapproved**. Append new, disjoint trips to existing `YYYY-MM.json` files while preserving every existing entry's values and order. Do not reject a month merely because it exists. Reuse standard-library JSON, SHA-256 and filesystem operations; no database or framework is needed. Record trip membership privately rather than adding photo identifiers to the public field schema.

Recommend one private JSON sidecar in the output directory containing committed trip memberships (sets of original-byte SHA-256 hashes, capture instants, selected month and entry digest) and, only while a batch is pending, its source/destination paths and content hashes, complete planned monthly JSON contents, monthly before/after hashes and progress. Persist the plan before moving anything. This is necessary evidence for retrying after originals have moved; regenerating from the remaining source alone could lose readings or append a partial duplicate. A simpler output-only approach cannot reliably recognize retries or newly supplied photos without either adding provenance to the approved public schema or requiring manual reconciliation after every interruption. Sidecar format, privacy and recovery behavior require approval; it is a private index and one pending operation record, not a generalized journal system.

Preflight reads all indexed trips, including neighboring months, before appending:

- Exactly matching membership hashes mean an already committed trip: do not append, rewrite its entry or move the repeated copies. Hash-identical input copies count once for proposed membership identity; retain/report extra copies without deleting them. This content deduplication is a proposed persistence policy, not an approved grouping change.
- Partial/shared membership, including a subset retry, stops for reconciliation. After removing exact repeats, rerun the existing approved grouping API on all persisted and new capture instants across months. Stop if a resulting group mixes new/indexed membership or changes any indexed trip's membership, including splitting or merging old groups. Thus old captures at minutes 2/5 plus new minute 1 stop at a three-minute window; old 0/3 plus new 4 may append as a separate trip. Do not silently extend or replace existing entries. This is repeat-run reconciliation using the approved partition, not a new classifier or dashboard trip-identity check. Reading/regrouping history costs memory and O(n log n) time; no workload limit or additional index is assumed.
- Append only trips outside those conflicts. Matching is supported only against intact sidecar provenance created by this process, using the same approved schema/grouping configuration. Missing/inconsistent provenance, changed monthly entries or incompatible configuration stop before effects; never infer identity from equal field values. Existing unindexed output needs explicit reconciliation, not automatic import.

Proposed effect order: acquire exclusive use of the output state; validate the complete batch and existing outputs; durably save its pending plan; move each original with verified copy-before-source-delete; then replace monthly JSON files with the planned complete contents; finally mark provenance committed and clear pending progress. Reserve collision names without overwrite. A source is deleted only after its destination's complete bytes match. Any copy, deletion or write failure stops further work and retains verified destinations, remaining originals and pending state. Earlier month replacements may already be visible; this is recoverable progress, not whole-batch rollback.

On restart, recover the pending plan before discovering new work. Compare actual files with recorded hashes: an already published planned month is complete, an unchanged old month can receive its planned replacement, and any unexpected content stops for resolution. Similarly verify existing destinations and remaining sources before resuming or completing deletions; never overwrite a changed file. Interrupted copies use temporary files and are reverified before publication. Repeated recovery must finish the same entries exactly once. Concurrent writers and ambiguous stale ownership must be refused, not assumed safe. Exact platform durability and exclusive-use mechanics remain implementation validation gates.

Proposed observables for user approval:

- Two equally latest clear values with identical approved parsed value/unit collapse to one; differing values or units stop before any moves/JSON changes. Unclear observations do not create such conflicts.
- A trip uses its earliest instant's metadata-local month. Equally earliest captures naming different local months stop preflight, even if later observations share a month.
- `photo.HEIC` collisions allocate `photo-01.HEIC`, then `photo-02.HEIC`, expanding beyond two digits. An already suffixed stem is retained (for example `photo-01-01.HEIC`); no existing file is overwritten. Source, destination and JSON directories must be disjoint, including no nesting or resolved links/reparse paths; overlap stops before effects.
- Repeating a completed trip leaves its existing monthly entry unchanged; adding a distinct trip to that month appends one entry. A subset or new photo that mixes/changes the stored partition stops instead of duplicating/updating it. Interrupting after source deletion, after one monthly replacement, or after all output writes but before marking the sidecar committed then recovering yields the same planned entries once, with all original bytes recoverable. An empty/no-match batch creates no new monthly records or moves.

Preflight stop proposals are specifically: unavailable required local decoder/OCR assets; decode/resource-limit or OCR execution failure; unresolved layout classification; a qualifying photo's missing/invalid original capture timestamp; conflicting equally latest clear values; ambiguous earliest local month; unsupported clear value representation/schema; unsafe/overlapping paths or inability to reserve output; invalid/inconsistent existing JSON/provenance, duplicate/overlap conflicts or pending recovery mismatch. Ordinary nonmatches continue; unreadable/absent fields follow earlier-clear/null rules. Write, copy, deletion and durability failures after effects begin use the recovery behavior above. No batch skip policy, metadata fallback or fabricated field value is proposed.
